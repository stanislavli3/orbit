# Deploy: hosted demo environment (Render)

Story SCRUM-41. One stable, hosted copy of Orbit with a SAMPLE dataset, so interview
demos don't depend on Wi-Fi or a laptop.

## Why Render

- **Blueprint** (`render.yaml`) describes the whole stack in the repo: API, Celery worker,
  Redis (Key Value), Postgres and the static frontend. One click creates all of it.
- Runs our existing pieces as-is: the backend is a Docker image (`backend/Dockerfile`),
  the worker is the same image with a `celery` command, the frontend is a static Vite build.
- Managed Redis + Postgres on a private network; secrets entered in the dashboard.
- One-click **Rollback** to any earlier deploy.
- Budget: roughly **$20/month** (API starter $7, worker starter $7, Postgres basic-256mb ~$6,
  Key Value free, static site free). Free web instances sleep and don't support the
  pre-deploy step, and there is no free worker, so starter is the minimum for a stable demo.
  Fly.io / Railway would also work but need more hand-written config for the same result.

File storage stays on S3 (or an S3-compatible bucket such as Cloudflare R2): Render disks are
per-service, so the API and worker could not share uploaded files.

## What is where

| Piece | Render service | Defined in |
| --- | --- | --- |
| Django API (gunicorn + whitenoise) | `orbit-api` (web, Docker) | `backend/Dockerfile`, `render.yaml` |
| Celery worker | `orbit-worker` (worker, Docker) | `render.yaml` (`dockerCommand`) |
| Celery broker | `orbit-redis` (Key Value, `noeviction`) | `render.yaml` |
| Database | `orbit-db` (Postgres 16) | `render.yaml`, `DATABASE_URL` |
| Frontend | `orbit-web` (static site, SPA rewrite) | `render.yaml` |
| CD | GitHub Actions `Deploy` | `.github/workflows/deploy.yml` |

Secrets live only in Render (shared env group `orbit-backend-secrets` for API + worker,
plus per-service values). Nothing is read from `backend/.env` in production: that file is
excluded from the image (`.dockerignore`). Local dev is unchanged: SQLite when
`DATABASE_URL` is unset, `make dev` as before.

On every API deploy, before traffic switches, Render runs:

```
python manage.py migrate --noinput && python manage.py seed_demo
```

If that fails, the deploy is aborted and the previous version keeps serving.

## One-time setup checklist

1. **Render account**: sign up at render.com with GitHub and grant access to this repo.
2. **Storage bucket**: create an S3 bucket (or R2 bucket) and an access key limited to it.
3. **Apply the Blueprint**: Render → **New → Blueprint** → pick this repo, branch `main`.
   Render reads `render.yaml` and asks for every `sync: false` value:
   - `CLERK_JWT_KEY`, `CLERK_ISSUER`: Clerk dashboard → API Keys (use the production instance).
   - `ANTHROPIC_API_KEY`.
   - `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_STORAGE_BUCKET_NAME`, `AWS_S3_REGION_NAME`;
     `AWS_S3_ENDPOINT_URL` empty for AWS, the R2 endpoint for R2.
   - Gmail OAuth (Story 3): `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`,
     `GMAIL_TOKEN_ENCRYPTION_KEY` (`python -c "import secrets; print(secrets.token_urlsafe(48))"`,
     set once and **never rotate**), `GMAIL_OAUTH_REDIRECT_URI` =
     `https://<api host>/api/team/gmail/oauth/callback/`.
   - `ALERT_WEBHOOK_URL`: optional, leave empty.
   - `orbit-api`: `ALLOWED_HOSTS` = `<api host>` (e.g. `orbit-api.onrender.com`),
     `CORS_ALLOWED_ORIGINS` and `CSRF_TRUSTED_ORIGINS` = `https://<web host>`,
     `DEMO_SEED_USERNAME` (see below; can be empty at first).
   - `orbit-web`: `VITE_API_URL` = `https://<api host>` (no trailing slash),
     `VITE_CLERK_PUBLISHABLE_KEY` = Clerk publishable key (`pk_live_...`).

   The host names are shown once the services exist. If you don't know them yet, enter a
   placeholder, then fix the values under each service → Environment and redeploy.
   `SECRET_KEY` is generated by Render. `DATABASE_URL` and `CELERY_BROKER_URL` are wired
   automatically from the database and Key Value instance.
4. **Google OAuth client**: Google Cloud Console → Google Auth Platform → Clients → the web
   client → add the exact `GMAIL_OAUTH_REDIRECT_URI` above to *Authorized redirect URIs*.
5. **Clerk**: add the `https://<web host>` origin to the Clerk production instance (allowed
   origins / domains).
6. **Verify settings**: `orbit-api` → **Shell**: `python manage.py check --deploy`.
   It should report no errors (the Gmail `bom_agent.E00x` checks pass once step 3 is done).
   HSTS subdomain/preload warnings (W005, W021) are expected and intentionally left off.
7. **Deploy hooks for CD**: for each of `orbit-api`, `orbit-worker`, `orbit-web` →
   Settings → **Deploy Hook** → copy the URL. In GitHub → Settings → Secrets and variables →
   Actions, add `RENDER_BACKEND_DEPLOY_HOOK`, `RENDER_WORKER_DEPLOY_HOOK`,
   `RENDER_FRONTEND_DEPLOY_HOOK`. Treat them as secrets: anyone with the URL can deploy.
8. **First deploy**: GitHub → Actions → **Deploy** → *Run workflow* (target `all`).
   Then open `https://<api host>/api/health/` and the web URL.

## How deploys happen

- **On merge**: when `CI` succeeds for a push to `main`, `Deploy` calls the three hooks with
  `ref=<tested commit>`. Render's own auto-deploy is off, so a failing CI never ships.
- **Manually**: Actions → Deploy → Run workflow (`all`, `backend` or `frontend`), or
  **Manual Deploy** in the Render dashboard.
- **No Render yet**: if the hook secrets are missing, `Deploy` succeeds with a
  "Deploy skipped" notice, so `main` stays green.

## Sample data for demos

`python manage.py seed_demo` seeds the clearly labelled SAMPLE part-cost history,
approved suppliers and quotes (`seed_part_history`) for `DEMO_SEED_USERNAME`. It runs on
every API deploy, is a no-op when the variable is empty, and is idempotent (re-running
replaces the earlier SAMPLE rows; real data is untouched).

Clerk users are stored as `clerk_<Clerk user id>`. To seed the demo account:

1. Create the demo user in Clerk (production instance) and sign in once on the hosted app.
2. Copy its user id (`user_...`) from the Clerk dashboard and set
   `DEMO_SEED_USERNAME=clerk_user_...` on `orbit-api`.
3. Redeploy, or seed right away from the `orbit-api` Shell: `python manage.py seed_demo`.

## Rollback

**Fast path (minutes): Render rollback.** Each service → **Events** → pick the last good
deploy → **Rollback**. Roll back `orbit-api` and `orbit-worker` together (same code), and
`orbit-web` if the UI changed. Rollback reuses the old build; it does not touch the database.

**Durable path: git revert.** Rollback alone is undone by the next deploy from `main`, so
also revert the bad change:

```
git revert <bad-merge-sha>        # use -m 1 for a merge commit
git push origin HEAD:<branch>     # open a PR, let CI pass, merge
```

CI passes → `Deploy` ships the reverted code.

**Database migrations: be careful.** Migrations run forward only on deploy, and Render
rollback does **not** reverse them.
- Prefer backward-compatible migrations (add nullable columns/tables first; drop or rename in a
  later release) so the previous code still runs against the new schema.
- If a release added an incompatible migration, reverse it from the Shell of the *still new*
  version before rolling back: `python manage.py migrate <app> <previous_migration>`.
- Before a risky migration, take a backup: Render → `orbit-db` → **Recovery** / export
  (point-in-time recovery needs a paid Postgres plan; otherwise `pg_dump` from a Shell).

```
docker build -f backend/Dockerfile -t orbit-api .   # context is the repo root (includes samples/)
DEBUG=False SECRET_KEY=x ALLOWED_HOSTS=localhost python manage.py check --deploy   # from backend/
```
